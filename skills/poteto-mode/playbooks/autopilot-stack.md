### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** The sibling of **Autopilot-full** (`pstack-cli playbook autopilot-full`).

**Tooling this playbook assumes.** The same as Autopilot-full. Owners and verifier lanes are Herdr-managed delegates from `pstack-cli run`, one worktree each, roles configured beforehand with `pstack-cli setup`. `gh` on PATH and authenticated, `origin` when the repository uses Origin. No `/loop`, no `/goal`, no `/deslop`, no cloud agents; the replacements are the ones Autopilot-full names. The root's own checkout is the only place topology is written, so keep a dedicated root worktree that no delegate uses.

1. **Run the owner loop unchanged.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If Origin is installed and resolves the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One delegate per PR owns its change end to end, launched in its own terminal or Herdr pane exactly as Autopilot-full step 2 shows (`git worktree add`, then `pstack-cli run --role "feature, refactoring" --cwd <owner-dir> --prompt <brief> --skill poteto-mode`): build, first push, a ready PR opened before self-proof, self-proof (gates, CI, receipts), skeptical bot and reviewer triage per `../references/bugbot-triage.md`, a slop-strip with the bundled **unslop** skill, a comment pass with the **no-comments** skill, and babysit to green per `pstack-cli playbook babysit`. Owners parallelize when the work is self-contained. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. Keep the trail uncommitted and return its path in the report. Owners also keep the `children.tsv` of Autopilot-full step 2.
2. **Audit on the wake chain.** The root runs an audit tick roughly every 30 minutes. The tick is the bounded shell loop from Autopilot-full step 6, waking on a delegate's `run` returning or on the 30-minute cap, whichever comes first. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook with `pstack-cli playbook autopilot-stack`, then re-read `goal.md`. Audit the operation against both. Fix drift during that tick. Probe each owner read-only through `pstack-cli status`, `pstack-cli read <worker>`, `gh pr view`, and pushed branches. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. Probe all delegates and end the tick per Autopilot-full step 6.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's explicit go, write the full program objective to `<store>/autopilot/<program-slug>/goal.md` and keep its todo item open. The goal continues across turns until the chain is done. On the operator's stop, every owner takes an immediate zero-writes hold, delivered and confirmed as in Autopilot-full step 7.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies each round per Autopilot-full step 4, with the same per-lane `pstack-cli run` launch in a worktree at the round SHA, and with STACK-READY in place of merge-ready. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. Say so in every owner brief. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer, and it writes from its own root worktree. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease` only after an `ls-remote` check, and set the PR base to the parent branch. Create it with `origin pr create --status open --base <parent-branch>` or `gh pr create --base <parent-branch>` according to the resolved forge. Retarget an existing PR with `origin pr edit <pr> --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk. Never submit or register the chain through `gt`.
7. **Absorb drift at the root, then re-verify what moved.** The root fetches current trunk and rebases the chain from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice (prompt its pane, or launch a fresh delegate in that owner's worktree with the conflict as the brief) and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up in the resolved forge, every link carrying its verifier verdict in the PR body or a comment. The root posts each verdict itself (`gh pr comment <pr> --body-file <verdict-file>` or `origin pr comment <pr> --body-file <verdict-file>`), since lanes have no forge credentials. The operator reviews and lands it, with their own clicks or by arming merge-when-ready. Landing is the Shipping playbook when the operator asks for it (`pstack-cli playbook shipping`).

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link with the lane worker names that produced it, anything parked or excluded with the reason, the owners' worktrees and trail paths, and which steps ran on a substitute for an upstream-only tool.
