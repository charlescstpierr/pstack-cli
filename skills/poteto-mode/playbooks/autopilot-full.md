### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

**Tooling this playbook assumes.** Owners and verifiers are Herdr-managed CLI delegates sent with `pstack-cli delegate` into sibling panes of the root's Herdr workspace, each in its own git worktree on this machine. There are no cloud agents. The roles you use (`feature, refactoring` or `hardest tasks` for owners, `judgment and prose` for verifier lanes) must already be configured with `pstack-cli setup --role "<role>" --kind <cli> --model <model>`, or `delegate` fails. `gh` must be on PATH and authenticated (`gh auth status`) for whoever pushes and merges. A delegate has no forge credentials unless its worktree inherits the machine's `gh` login, so the brief states whether the owner may run `gh pr create` and `gh pr merge` itself or must report merge-ready and let the root do it. Upstream names `/deslop` from `cursor-team-kit`, `/goal`, and a terminal `/loop`. None of those exist here. Their replacements are named inline: the bundled `unslop` skill for the slop-strip, a written goal file for the goal, and your own bounded audit loop for the cadence. Bugbot is an external GitHub App. If the repository doesn't have it installed, the Bugbot triage step becomes triage of whatever review bots and human reviewers the repo does have, and the reply says so.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go. On that go, write the full program objective to `<store>/autopilot/<program-slug>/goal.md` (the queue, who merges what, the verification rule, the done condition) and open a todo item that stays open until the queue is done. That file is the `/goal`. Re-read it at every audit tick. The goal continues across turns until the queue is done.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If Origin is installed and resolves the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One delegate per PR, in its own worktree, launched in its own terminal or Herdr pane:

   ```bash
   git worktree add <owner-dir> -b <branch> origin/main
   pstack-cli delegate --task-id <id> --role "feature, refactoring" --cwd "<owner-dir>" --prompt "<owner brief>" --skill poteto-mode
   ```

   The owner brief carries the whole lifecycle: build, the first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical triage of every bot and reviewer comment per `../references/bugbot-triage.md`, a slop-strip with the bundled **unslop** skill (`pstack-cli skill unslop`), a comment pass with the **no-comments** skill (`pstack-cli skill no-comments`), a rebase onto current trunk, the babysit loop to green (`pstack-cli playbook babysit`), and the merge itself when the brief grants it. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft (`gh pr create --base main` or `origin pr create --status open --base main`). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return its path with the reports. As soon as the owner starts a delegate of its own, it adds that delegate's worker name, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after the slop-strip and the comment pass, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.

   `delegate` returns once the brief is submitted. Read the owner with `pstack-cli collect <id> --wait <ms>`. A `blocked` owner is waiting at a prompt in its pane. `unknown` or `mismatch` means the pane can't be trusted, so never resend an id on an ambiguous status. The owner's reports (code-ready SHA, merge-ready SHA, `decisions.tsv` path) come out of its confirmed result, not from memory. When a round's findings need to go back, collect and `pstack-cli dismiss` the old id, then send a fresh `delegate` with a new task id, the same owner worktree, and one consolidated fix-forward brief.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, one worktree per owner, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack. Size the parallel pool to this machine; `pstack-cli tasks` shows what's running.
4. **Swarm-verify every round before its merge.** A round starts at the owner's code-ready head SHA and at each later push that changes the PR's patch. At that SHA, fan out parallel independent verifiers per the **swarm** skill (`pstack-cli skill swarm`) and aggregate to one verdict. Each lane is its own delegate in its own worktree checked out at the round SHA, on the role the swarm skill prescribes, and never on the role that wrote the code:

   ```bash
   git worktree add <lane-dir> <head-sha>
   pstack-cli delegate --task-id <id> --role "judgment and prose" --cwd "<lane-dir>" --prompt "<lane brief>" --skill poteto-mode
   ```

   The merge needs a clean verdict from the round whose patch matches the merge-ready head. Audit the receipts in the merge-ready report before the verdict. The lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (with `control-cli` or `control-ui` if one is installed for this CLI, otherwise a scripted driver the lane brief names; "inconclusive" is not a pass). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. Each lane returns one line `PASS`, `PASS+NOTES`, or `FAIL` followed by evidence; you read it with `pstack-cli collect <id>` and aggregate yourself. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh swarm and a fresh verdict, except for lane results that stay valid under the patch-id rule in `playbooks/shipping.md`.
5. **On a clean verdict the owner merges and takes the next item.** The owner merges only from a head freshly rebased onto trunk. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the round's verdict still holds. If trunk moves again before the merge, the patch-id rule in `playbooks/shipping.md` governs re-verification. A new head voids the verdict unless the patch-id is unchanged. The owner squash-merges its own PR through the resolved forge (`gh pr merge <pr> --squash` or `origin pr merge <pr> --squash`) and picks up its next self-contained item from the queue by a fresh prompt from you. If the owner's worktree has no forge credentials, the root runs the merge command itself after the owner reports merge-ready; it is still the owner's merge, gated the same way. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners roughly every 30 minutes. There is no `/loop` command here. The cadence is a bounded loop you hold yourself in a monitored shell: wait on the owners' background jobs with a 30-minute cap (a loop of `pstack-cli collect <id> --wait <ms>` across owners, capped at 30 minutes), and treat each return or cap expiry as the tick. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook with `pstack-cli playbook autopilot-full`, then re-read `goal.md`. Audit the operation against both. Fix drift during that tick. Probe each owner read-only with `pstack-cli tasks` and `pstack-cli collect <id>`, plus `gh pr view` and pushed branches, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Stand it down and dispatch a replacement at once with a fresh consolidated brief. Do not wait for a polite return. Each tick also runs the lane stuck test over `pstack-cli tasks` and over every owner's `children.tsv`. Whether or not a stop works, the root has the owner record each stuck delegate as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick only when no delegated work is left, even after the last merge.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately: send each running owner the hold as a fresh `delegate` into its worktree after dismissing the old id, or dismiss it outright, and confirm through `pstack-cli tasks` and `git status` in each worktree that nothing is still writing. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner (worker name and worktree), state, and head SHA. Each verdict and the swarm that produced it, with each lane's worker name. What merged and what each owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails and `goal.md` live. Which steps ran on a substitute (unslop for deslop, `gh` polling for the watcher, a scripted driver for a missing control skill).
